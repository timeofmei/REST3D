# 2026-08-01

## 问题 0：RTX 5090 CUDA 兼容性

### 现象

在原 `rest3d` 环境中运行 `1_infer_scenecanon.sh` 时，PyTorch 首先提示：

```text
NVIDIA GeForce RTX 5090 D v2 with CUDA capability sm_120 is not compatible
with the current PyTorch installation.
The current PyTorch install supports CUDA capabilities ... sm_90.
```

随后 SAM3 在创建 CUDA tensor 时失败：

```text
RuntimeError: CUDA error: no kernel image is available for execution on the device
```

原环境的主要版本为：

- `rest3d`：Python 3.11、PyTorch `2.5.1+cu121`；
- `gym`：Python 3.8、PyTorch `2.2.2+cu121`；
- GPU：RTX 5090 D v2，Compute Capability `sm_120`。

两个 PyTorch cu121 wheel 都只包含到 `sm_90` 的 CUDA kernel，因此
`torch.cuda.is_available()` 虽然返回 `True`，实际执行 CUDA kernel 时仍会失败。

### 根因

#### 1. `rest3d` 的 PyTorch wheel 不包含 `sm_120`

RTX 5090 属于 Blackwell 架构，需要包含 `sm_120` kernel 的 PyTorch/CUDA 构建。
原来的 PyTorch 2.5.1 cu121 可以加载 NVIDIA 驱动并识别 GPU，但不能在 5090
上执行诸如 `torch.zeros(..., device="cuda")` 的操作。

#### 2. CUDA 扩展仍按 CUDA 12.1 或旧 PyTorch ABI 构建

Stage 2 依赖 PyTorch3D、Kaolin、spconv、gsplat 和 Warp 等 CUDA 组件。即使只升级
PyTorch，原先为 CUDA 12.1 和 PyTorch 2.5.1 安装的二进制扩展也可能出现：

- 找不到或无法加载扩展 `.so`；
- PyTorch ABI 不匹配；
- 扩展没有 `sm_120` kernel；
- 运行时再次出现 `no kernel image`。

项目代码还曾无条件把 `CUDA_HOME` 指向当前 Conda 环境，使扩展继续使用环境内
的 CUDA 12.1 编译器，而不是系统已安装的 CUDA 12.8。

#### 3. Isaac Gym Preview 4 不能直接升级到相同的 PyTorch

Isaac Gym Preview 4 只提供 Python 3.6–3.8 的预编译绑定，而支持 Blackwell 的
新 PyTorch 版本不再提供 Python 3.8 wheel。因此 `gym` 环境不能简单照搬
`rest3d` 的 PyTorch 2.7.1 cu128 方案。

Isaac Gym 中 GPU PhysX 和 GPU tensor pipeline 是两个独立选项。旧 PyTorch
不能在 5090 上运行 tensor kernel，但 Isaac Gym 自带的 PhysX 仍可以使用 5090
进行物理仿真。

### 解决方案

#### 1. 升级 `rest3d` Conda 环境

先复制环境进行验证，确认可用后再将其切换为正式的 `rest3d` 环境。当前配置为：

- Python 3.11；
- PyTorch `2.7.1+cu128`；
- torchvision `0.22.1+cu128`；
- torchaudio `2.7.1+cu128`；
- CUDA Toolkit `/usr/local/cuda-12.8`。

旧环境保留为 `rest3d-cu121-backup`，便于需要时回退。

通过 Conda 环境变量为 `rest3d` 自动设置：

```text
SAM3D_OBJECTS_ROOT=/home/yangyankun/sam-3d-objects
CUDA_HOME=/usr/local/cuda-12.8
TORCH_CUDA_ARCH_LIST=12.0
```

激活环境后，PyTorch 的 architecture list 已包含 `sm_120` 和
`compute_120`，普通 CUDA tensor 操作可以直接在 RTX 5090 上执行。

#### 2. 重新安装或编译 Stage 2 CUDA 扩展

- 安装与 PyTorch 2.7.1/cu128 匹配的 Kaolin 0.18.0 wheel；
- 使用 CUDA 12.8、`TORCH_CUDA_ARCH_LIST=12.0` 从源码编译 PyTorch3D；
- 移除旧的 `xformers` 和 `flash-attn` 二进制扩展；
- RTX 5090 路径使用 PyTorch SDPA；
- 对 spconv、gsplat 和 Warp 分别执行真实 CUDA 运算验证。

同时修改 `rest3d/models/build_sam3dobj.py`：优先尊重外部设置的
`CUDA_HOME`，未设置时优先查找 `/usr/local/cuda-12.8`，不再无条件使用
Conda 环境内的 CUDA 12.1。

#### 3. 为 `gym` 自动选择兼容的 Isaac Gym 模式

保留 Isaac Gym Preview 4 所需的 Python 3.8 和 PyTorch 2.2.2 cu121，并将两个
GPU 选项解耦：

```text
PhysX device:       cuda:0
GPU PhysX:          enabled
GPU tensor pipeline: disabled
State tensor device: CPU
```

代码会读取当前 GPU Compute Capability 和 `torch.cuda.get_arch_list()`：

- 如果 PyTorch 支持当前 GPU，启用 GPU PhysX 和 GPU tensor pipeline；
- 如果 PyTorch 不支持 `sm_120`，保留 GPU PhysX，但使用 CPU tensor pipeline；
- 如果用户强制启用不受支持的 GPU tensor pipeline，则直接给出明确错误。

该逻辑同时应用在稳定化 CEM 和 simulator replay 中。这里的 CPU tensor pipeline
只负责 Isaac Gym 与 Python 之间的状态交换，物理计算仍由 RTX 5090 上的 GPU
PhysX 执行。

### 验证结果

`rest3d` 环境已完成以下实际 CUDA 验证：

- PyTorch 创建和计算 CUDA tensor；
- SAM3 模型构建及真实图片分割；
- PyTorch3D `knn_points`；
- Kaolin SPC 操作；
- spconv 稀疏卷积；
- gsplat rasterization；
- Warp CUDA 数据操作；
- SAM 3D Objects 对完整场景中的多个 mask 进行三维重建。

`gym` 环境已验证：

- Isaac Gym 成功创建 `cuda:0` PhysX simulation；
- 日志显示 `+++ Using GPU PhysX`；
- 本地组 CEM、全局 CEM 和墙面后处理运行完成；
- simulator replay 能加载完整场景并执行物理步进。

最终兼容策略是：Stage 1–2 使用原生支持 `sm_120` 的 PyTorch cu128；Stage 3
使用 GPU PhysX 配合 CPU tensor pipeline，从而避免旧 PyTorch 在 5090 上启动
不受支持的 CUDA kernel。

## 问题 1：`1_infer_scenecanon.sh` 运行缓慢

### 现象

使用下面的输入运行 Stage 1–2：

```text
data/my_capture_frame145_centered_meters/images/cam_22.png
```

`1_infer_scenecanon.sh` 大约 45 分钟后才结束，运行期间观察到 RTX
5090 显存接近占满。输入图片分辨率为 `3134 × 4292`，约 1345 万像素。

### 实际耗时拆分

根据 `output/cam_22/stage1/` 和 `output/cam_22/stage2/` 下的日志及文件时间：

| 阶段 | 大致耗时 | 内容 |
| --- | ---: | --- |
| Stage 1：对象列表识别 | 约 25 秒 | Gemini 从图片中列出对象类别 |
| Stage 1：对象分割代理 | 约 22 分钟 | Gemini 和 SAM3 多轮交互，为每类对象生成并选择 mask |
| Stage 1：场景树构建 | 约 20 分钟 | 对 17 个对象逐一调用 Gemini 判断 parent/relation/type |
| Stage 2：模型初始化 | 约 35 秒 | 加载 SAM 3D Objects、DINO 等模型 |
| Stage 2：18 个 mask 三维重建 | 约 2 分 19 秒 | 稀疏结构生成、网格解码、对齐和规范化 |

因此，约 43 分钟消耗在 Stage 1，Stage 2 的本地 5090 推理不是主要瓶颈。

### 主要原因

#### 1. Gemini 请求使用了未缩放的高分辨率 PNG

`rest3d/utils/vlm.py` 会把 PIL 图片重新编码成 PNG/base64 后发送。当前没有
为 VLM 单独创建低分辨率副本，所以原图和所有 mask overlay 都保持
`3134 × 4292`。本次生成的单张 overlay 大约为 9.5 MB。

场景树为每个对象构造的请求最多包含：

- 1 张原图；
- 1 张当前对象的 overlay；
- 5 张附近对象的 overlay。

也就是说，一次请求最多携带 7 张完整分辨率图片，编码后可能达到几十 MB。
这些图片需要反复编码、上传并由远程模型预处理。

#### 2. 场景树对 17 个对象串行请求 Gemini

最初只识别了 7 类对象，但分割后包含：

- 10 个 `white_vertical_light_panels`；
- 4 个 `white_ceiling_light_panels`；
- 桌子、椅子、键盘等其他对象。

场景树最终包含 17 个对象。当前实现逐对象调用 Gemini，前一个请求结束后才
开始下一个请求，没有批处理或并发。该步骤从约 15:33:39 运行到 15:53:55，
单独消耗约 20 分钟。

#### 3. 分割代理进行了大量提示词和 API 重试

本次在 `segment_agent_out/sam_out/` 中产生了约 26 组 SAM3 中间结果：

- 天花板灯板尝试了约 8 个不同的文本提示；
- `metal frame structure` 尝试了约 11 个提示，最终仍未得到可接受结果；
- 日志中存在 Gemini 响应缺少 `<tool>` 标签后的额外请求。

部分中间结果之间出现接近 60 秒、120 秒的空档，与 Gemini 429 限流时的
指数退避等待一致。当前 Gemini 重试逻辑在限流后依次等待
`60、120、240、480` 秒，因此少数失败请求就可能增加数分钟。

#### 4. 重复实例没有复用判断结果

10 个墙面灯板和 4 个天花板灯板分别进行分割选择和场景树 parent 判断。
这些同类、同安装方式的对象没有共享 VLM 结论，造成大量内容高度相似的请求。

#### 5. Stage 1 缓存不完整

已有对象 mask 可以部分复用，但仍存在两个问题：

- floor 实际文件名是 `the_floor.png`，通用缓存检查使用
  `the_floor_*.png`，因此不能正确命中；
- `scene_tree.json` 即使已经存在，也会重新对所有对象请求 Gemini。

因此同一张图片重跑时，Stage 1 仍可能再次消耗较长时间。

### 显存占满是否导致变慢

目前没有发现 CUDA OOM、kernel 重试或 `no kernel image` 错误。Stage 2 会同时
加载 SAM 3D Objects、DINO、spconv 等组件，而且 PyTorch 的缓存分配器会保留
已经申请的显存，所以 `nvidia-smi` 显示接近占满并不等于发生了显存泄漏。

本次 Stage 2 在约 2 分 19 秒内完成了 18 个 mask 的三维重建，说明显存占用
不是 45 分钟总耗时的主要原因。需要优先优化的是 Stage 1 的远程 VLM 调用。

### 建议的解决方案

#### 优先级 1：为 VLM 创建低分辨率图片

仅在发送 Gemini 时将原图和 overlay 缩放到长边 `1280` 或 `1536`；SAM3 和最终
mask 仍可使用原始分辨率，避免影响输出尺寸。

建议在 VLM 编码入口统一处理，而不是在每个调用点重复实现：

1. 保持图片纵横比；
2. 超过最大边长时使用高质量下采样；
3. 场景树的原图和 overlay 使用相同缩放尺寸；
4. 对同一图片的编码结果做内存缓存，避免每次请求重新 PNG 编码。

这是改动较小、收益最直接的优化。

#### 优先级 2：批量构建场景树

不要为每个对象单独请求一次 Gemini。可改为：

- 一次请求处理全部对象；或
- 每批处理 4–8 个对象；
- 将所有编号 mask 制作成一张或少数几张低分辨率总览图；
- 要求 Gemini 一次返回结构化 JSON 数组。

这样可以把当前 17 次大图片请求压缩为约 1–4 次，并减少重复上传原图。

#### 优先级 3：合并同类重复实例

对于墙面灯板、天花板灯板等重复实例：

- 先按原始对象类别分组；
- 对一组实例一次性判断 parent/relation/type；
- 必要时仅对几何位置异常的实例单独复核。

本次 14 个灯板实例理论上不需要 14 次独立的 parent 请求。

#### 优先级 4：限制无效的代理重试

建议区分三类失败：

- Gemini 格式错误：只追加一次“仅输出 tool JSON”的格式修复请求；
- SAM3 返回空 mask：限制同义词尝试数量，例如最多 3–4 个；
- API 429：记录限流次数并尽早停止当前非关键对象，而不是持续指数等待。

对于 `metal frame structure` 这类连续多次失败的对象，可以允许跳过或使用已有
mask 的几何兜底，避免单个非关键对象消耗数分钟。

#### 优先级 5：完善缓存

建议为 Stage 1 增加 manifest，记录：

- 输入图片哈希；
- 对象列表及 prompt 版本；
- mask 文件哈希；
- VLM 模型名；
- scene tree 结果。

当图片、prompt 和 mask 都未变化时，直接复用 `scene_tree.json`。同时对
`the_floor.png` 做专门的缓存命中处理。

#### 优先级 6：增加阶段计时和 API 统计

日志中应记录：

- 每次 Gemini 请求的开始/结束时间；
- 请求图片数量、尺寸和编码后字节数；
- 429、格式重试和 SAM3 同义词重试次数；
- 每个对象在 VLM、SAM3 和文件处理上的耗时；
- Stage 1/2 模型初始化时间和峰值显存。

这样后续可以直接判断是本地 GPU、网络上传、API 限流还是代理策略导致变慢。

### 推荐实施顺序

1. VLM 图片缩放与编码缓存；
2. 场景树批处理；
3. 修复 floor 和 scene tree 缓存；
4. 限制同义词及格式重试；
5. 合并重复实例并补充详细计时。

前两项能直接消除本次运行中最大的两个瓶颈。实际耗时仍会受到 Gemini 服务
延迟和账号配额影响，但正常情况下不应再为 17 个对象反复上传几十 MB 的图片。
